# AFRIPAY review — 11 November 2026

## Assessment

AFRIPAY is a working invoice/payment prototype with a clear distinction between simulated credits, native blockchain payments and cross-chain conversion. Its strongest product combination is invoice review, explainable recipient checks and human-approved wallet payments. The latest deployment contains the invoice inbox, supplier dashboard, notifications and mainnet upload entry screens.

Before submission, record funded BSC/Intents execution evidence. Two founder-supplied native NEAR mainnet transfers are now independently verified. Two additional testnet transfers were also verified; see [Verified transactions](../VERIFIED-TRANSACTIONS.md).

## Independently checked on the deployed site

- Public site and feature routes returned HTTP 200. Public configuration reported v0.9.5, configured authentication and enabled mainnet funding.
- Desktop and mobile browsers loaded Demo, invoice inbox, supplier dashboard, notifications, mainnet upload and the new-payment entry page. No JavaScript page errors or horizontal overflow were observed in these views.
- The guided guest invoice reached extracted-field review. A direct deterministic extraction check returned the expected sample invoice number, supplier, 200 USDC amount, Base address/network and due date, with `requiresVerification: true`.
- Public asset discovery returned HTTP 200 and 229 supported assets at review time. This verifies discovery availability, not successful swap execution or token balances in a particular wallet.
- Private business invoice, notification, live-order and payment-request APIs returned HTTP 401 without authentication. This checks the anonymous access boundary; it does not establish every authenticated permission in production.
- The GitHub repository and its current public README were reachable.
- The previously supplied testnet transfer was rechecked through public RPC: final successful execution, 0.01 test NEAR, `alephai.testnet` → `afripayai.testnet`, hash `55jZE7gnpLRzhUySa2NtqxMRp6PuxfqFcWhzmECiHWGa`.

## Local code and regression evidence

A fresh local run passed **408 tests in 46 files** and TypeScript. The latest feature work also passed the production build, 44-route smoke check, 154 desktop/mobile browser regressions and eight final focused browser checks after document-review invalidation was added.

The tested controls include participant-only invoice access; explicit administrator supplier review; invoice delivery atomicity/idempotency; destination/asset binding; one active payment per invoice; payment identity separated from a shared human reference; exact native/BSC signing builders; canonical settlement evidence; spending caps; recovery of uncertain submissions; private/deduplicated notifications; exact native amounts; and invoice/receipt PDF generation.

Database tests use embedded PostgreSQL with the actual migrations. Browser tests use isolated auth/API/wallet fixtures. These support implementation claims but are not independent funded-wallet, email-delivery or live-private-inbox acceptance evidence.

## Documentation issues corrected

1. The public README described the earlier release and omitted the private invoice inbox, supplier dashboard, notification and upload-review workflows. The replacement documents the current product flow and keeps a concise entry point.
2. Historical setup documents had conflicting “run LAST” instructions, including an old statement that no server service key was needed. A new current `SETUP.md` gives the complete dependency order and separates public/client settings from server-only settings. Historical documents now point to that guide.
3. Payment evidence is now separated by mode. The founder's mainnet report is now supported by two independently checked native transfer records; private invoice/app linkage is not inferred from the chain records alone. Token discovery and dry-quote integration are not presented as funded cross-chain proof.
4. Documentation states the source-wallet network correctly: NEAR-funded cross-chain approval remains on NEAR; direct BSC requires an EVM wallet on chain 56 and BNB gas.
5. Reporting and security limits are explicit: tracked activity is not complete external wallet history, BSC is separate from NEAR-order CSV, asset totals are not invented USD valuations, and explainable checks do not guarantee safety.

## Additional transaction proof verified

Mainnet and testnet evidence remain separate. [Details and raw observations](../VERIFIED-TRANSACTIONS.md).

## Remaining acceptance work

- Demonstrate private invoice delivery between two real accounts, then verify both parties' Paid state, notifications and PDFs after an intentional wallet-approved payment. The anonymous reviewer did not access these accounts or their private database rows.
- Record a funded BSC transfer and a funded NEAR Intents cross-chain settlement before claiming either route as demonstrated end to end.
- Test configured model and email delivery separately if they will appear in the final demonstration. The live extraction check used local deterministic extraction, not a hosted model.

Market-price features remain future work. They do not replace the payment evidence above.
