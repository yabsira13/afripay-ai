# Accounts, Pay / Receive, supplier registration and admin review

## Install this update

1. Stop the previous server with Ctrl+C.
2. Extract the full updated ZIP to a new folder and open its `afripay-ai` folder in VS Code.
3. **Copy your own `.env.local` from the old project into the new project.** Downloaded archives never include your settings.
4. Run `npm.cmd ci`, then `npm.cmd run dev`.
5. Open the same http://localhost:3000 address and refresh with Ctrl+Shift+R.

## Email confirmation

A successful signup with no active session now replaces the form with a persistent **Check your email** screen. It shows the submitted address, instructions, a Sign in button and a rate-limited resend button. Errors stay visible. If email confirmation is disabled in your Supabase project and the service returns an active session, the app signs in rather than pretending to send a confirmation message.

Supabase settings: enable the Email provider and confirmation under Authentication. Set Site URL to `http://localhost:3000` during local testing, and add `http://localhost:3000/auth` and `http://localhost:3000/auth/reset` to allowed Redirect URLs. Use the deployed HTTPS origin after publishing. Public signups need working email delivery; Supabase's default sender has limits. Use a supported SMTP provider before opening public registration widely.

No actual signup or confirmation email was generated by the automated tests in this workspace.

## Pay and Receive

Pay is visible separately from Receive in the sidebar and dashboard. Demo Pay now accepts a **New / custom recipient**, rather than only the seeded suppliers. Address format, risk rules, limits and approval still apply. No real transfer is executed.

Receive displays only a connected mainnet NEAR wallet account, with a copy button and native NEAR network label. It never substitutes a fictional receive address. It does not register an asset on-chain, reconcile incoming transfers, update invoices or generate a real financial receipt. Do not send EVM/Base USDC directly to a NEAR account ID. A connected wallet is not automatically linked to the email account or verified as owned by the supplier.

## One Supabase database setup step

The supplier module uses real authenticated Supabase rows independently of the unfinished business/payment database integration.

1. In Supabase open **SQL Editor → New query**.
2. In VS Code open `supabase/supplier-marketplace.sql`.
3. Copy its contents into the SQL Editor and click **Run**.
4. Keep this SQL migration in your repository. It contains no account passwords or keys.

This creates supplier applications, protected administrator membership, review logs and server-enforced row access rules. The normal signup screen cannot appoint administrators.

## Make the founder an administrator

1. Confirm and sign into your AFRIPAY account once.
2. In Supabase open **Authentication → Users**, locate that email and copy its **User UID**.
3. In SQL Editor run the query below after replacing the placeholder with your actual UID:

```sql
insert into public.afripay_admins(user_id)
values ('YOUR-ACTUAL-AUTH-USER-UUID')
on conflict do nothing;
```

Only the project operator should do this. Do not put a secret/service-role key in the frontend. There is no public "become admin" API.

4. In AFRIPAY open **Admin review**. A non-admin account will see Access denied. A founder account with the membership above can review applications.

## Supplier flow

1. A user creates and confirms an AFRIPAY account.
2. They open **Become a supplier**, enter business name, country, public wallet and chain, then submit.
3. The application is **pending** and not visible to other ordinary users.
4. The administrator independently checks the business and wallet, ticks the verification box, and approves or rejects it.
5. Approved applications appear in **Suppliers** in Live view or **Registered supplier directory** from Demo.
6. The directory can load a recipient into a clearly labeled demo proposal. It does not enable a live funded payment.

Every owner edit, including an approved wallet change, resets the application to pending and clears verification. Admin approval is bound to the wallet, chain and application version actually reviewed; a changed application must be reloaded and reviewed again. Review notes are not public. Approval is human moderation, not on-chain ownership verification or identity certification.

## Two-account test — no real funds

Use two email addresses you control. Do not share passwords with the assistant.

- **Account A:** regular browser window; founder/buyer, optionally appointed administrator through the SQL step.
- **Account B:** a separate browser profile or private window; supplier account.

Confirm each email in its corresponding browser profile. Account B submits a supplier application. Account A reviews it. Check that B cannot open the admin panel, and that only approved suppliers appear in the directory. Then A can load B's address into a demo payment proposal and run the simulation.

**A simulated payment will not credit B, appear as real incoming funds or move money between wallets.** Two email accounts are not two wallets. A future real transfer requires two different wallets and the unfinished funded-payment coordinator, with explicit authorization and verified settlement. We should not attempt that real transfer yet.

## Browser demo data

Each signed-in user now has a separate browser-local demo workspace. Guest data from the old version is preserved in the guest workspace and is not assigned to the first person who signs in. Thus a new account starts with fresh seeded examples; your old guest records are still accessible after signing out.

This prevents ordinary account switching from mixing demo histories. It is not encryption or a production authorization boundary: someone with access to your browser storage can inspect it. Production invoice/payment persistence remains unfinished. Supplier rows, in contrast, use server-side PostgreSQL policies.

## Verification and limits

The supplier SQL policies are tested using embedded PostgreSQL (PGlite) with an emulated Supabase auth context. Tests cover non-owner access, self-appointed admins, forged approvals, pending/approved visibility, reviewed-wallet changes and audit visibility. These are actual PostgreSQL policy tests, not just string checks, but they do not replace verification against your hosted Supabase project.

The browser signup, email delivery, copy-address interaction and actual Supabase migration still need your PC/project test. No private keys, real transfers or live payment receipts are implemented by this update.

The previously observed invoice-number bug (“FOR” extracted from a demo banner) is fixed in this update. Explicit invoice-number labels are preferred; ambiguous headings require manual review.
